# Persona-Dough 專案現狀分析報告

**生成日期：** 2026年1月24日  
**分析範圍：** 完整專案結構與程式碼  
**目的：** 為專案交接提供全面的技術分析

---

## 一、專案概述

這是一個基於 FastAPI 的 **LLM 驅動的人格代理人模擬系統**，整合了角色生成、對話模擬、生活行程管理和場景模擬等多個功能模組。

### 專案規模統計
- **核心 Python 檔案：** 25+ 個
- **主要模組目錄：** 5 個（module、humanoid、interviewer、simulation_framework、conversation_history）
- **主後端檔案：** backend.py（3495 行）
- **總程式碼行數：** 約 10,000+ 行

---

## 二、主要功能模組分析

### 2.1 後端伺服器層 (Backend Layer)

#### **backend.py** - 主要 API 伺服器
- **職責：** FastAPI 主應用程式，整合所有子系統的 API 端點
- **行數：** 3495 行（⚠️ 過於龐大）
- **管理的全域物件：**
  - `character_generator` - 角色生成器
  - `dialogue_manager` - 雙人對話管理器
  - `group_dialogue_manager` - 群組對話管理器
  - `active_simulations` - 火災模擬管理器（字典）
  - 隱式依賴 `life_simulation_manager`（從其他模組導入）
  - 隱式依賴 `llm_scheduler`（從其他模組導入）
  - 隱式依賴 `location_manager`（從其他模組導入）

#### **life_simulation_backend.py** - 生活模擬系統
- **職責：** 管理代理人的日常生活行程與狀態
- **行數：** 722 行
- **核心類別：**
  - `LifeSimulationManager` - 生活模擬主管理器
  - `AgentStatus` - 代理人狀態數據
  - `DailySchedule` - 每日行程
  - `ScheduledTask` - 排程任務
- **全域實例：** `life_simulation_manager = LifeSimulationManager()`

#### **llm_scheduler.py** - LLM 智能排程系統
- **職責：** 使用 LLM 根據角色個性生成個性化活動
- **行數：** 479 行
- **核心類別：**
  - `LLMScheduler` - LLM 排程器
  - `PersonalityProfile` - 個性檔案
  - `ActivityRequest` - 活動生成請求
  - `GeneratedActivity` - 生成的活動
- **全域實例：** `llm_scheduler = LLMScheduler(use_ollama=True)`

#### **location_function_tools.py** - 位置管理工具
- **職責：** 管理遊戲世界中的地點和角色位置記憶
- **行數：** 796 行
- **核心類別：**
  - `SmartLocationManager` - 位置管理器
  - `LocationInfo` - 位置資訊
  - `CharacterLocationStatus` - 角色位置狀態
  - `CharacterLocationMemory` - 角色位置記憶
- **全域實例：** `location_manager = SmartLocationManager()`

#### **scenario_simulator.py** - 場景模擬器
- **職責：** 火災等緊急場景的模擬
- **行數：** 924 行
- **核心類別：**
  - `FireScenarioSimulator` - 火災模擬器
  - `Agent` - 場景代理人
  - `Room` - 房間環境

## 三、目前結構的三大問題

### ⚠️ 問題 1：單體巨型檔案（Monolithic Backend）

#### **問題描述：**
`backend.py` 有 **3495 行**，包含了所有的 API 端點定義，嚴重違反單一職責原則。

#### **具體表現：**
- 包含 **80+ 個 API 端點**，涵蓋：
  - 角色生成（15+ 個端點）
  - 對話系統（10+ 個端點）
  - 生活模擬（15+ 個端點）
  - 火災模擬（10+ 個端點）
  - 位置管理（8+ 個端點）
  - LLM 排程（8+ 個端點）
  - Unity 整合（5+ 個端點）
  - 記憶管理（5+ 個端點）
  - 群組對話（5+ 個端點）
- 在檔案中直接定義了多個類別：
  - `GroupDialogueManager`
  - `UnityMemoryRequest` / `UnityMemoryResponse`
  - 大量 Pydantic Model

#### **影響：**
- **可維護性極差：** 任何修改都需要在 3495 行中找到對應位置
- **團隊協作困難：** 多人修改容易產生 merge conflict
- **測試困難：** 端點耦合在一起，難以進行單元測試
- **啟動時間長：** 所有模組都要載入

#### **建議改進方向：**
應該拆分為：
```
routers/
  ├── humanoid_router.py       # 角色生成相關
  ├── dialogue_router.py        # 對話相關
  ├── simulation_router.py      # 生活模擬相關
  ├── scenario_router.py        # 場景模擬相關
  ├── location_router.py        # 位置管理相關
  ├── scheduler_router.py       # 排程相關
  └── unity_router.py           # Unity 整合相關
```

---

### ⚠️ 問題 2：隱式的循環依賴與全域單例混亂

#### **問題描述：**
專案中存在多個**全域單例物件**，在不同檔案中被交叉引用，形成隱式的循環依賴風險。

#### **全域單例清單：**

| 物件名稱 | 定義位置 | 使用位置 | 類型 |
|---------|---------|---------|------|
| `character_generator` | backend.py L65 | backend.py 內部 | CharacterGenerator |
| `dialogue_manager` | backend.py L1229 | backend.py 內部 | PersonaDialogueManager |
| `group_dialogue_manager` | backend.py L1230 | backend.py 內部 | GroupDialogueManager |
| `life_simulation_manager` | life_simulation_backend.py | backend.py, 自身模組 | LifeSimulationManager |
| `llm_scheduler` | llm_scheduler.py | backend.py | LLMScheduler |
| `location_manager` | location_function_tools.py | backend.py, llm_scheduler.py | SmartLocationManager |
| `active_simulations` | backend.py L78 | backend.py 內部 | Dict |

#### **具體問題：**

1. **模組級導入副作用：**
```python
# backend.py
from llm_scheduler import llm_scheduler, ActivityRequest, ContextInfo
from location_function_tools import location_manager
from life_simulation_backend import life_simulation_manager
```
這些導入會立即執行模組級別的程式碼，創建全域單例。

2. **交叉依賴鏈：**
```
backend.py 
  ↓ 導入
llm_scheduler.py 
  ↓ 導入
module/LLM_responder.py
module/PERSONA_loader.py
  ↓ 導入
aiofiles, asyncio, ...
```

3. **初始化時機不明確：**
- 部分物件在導入時就初始化（如 `life_simulation_manager`）
- 部分物件需要延遲初始化（如 `PersonaLoader`，需要 `await wait_until_ready()`）
- 不同的初始化模式混雜在一起

#### **實際案例：**
```python
# llm_scheduler.py
class LLMScheduler:
    def __init__(self, use_ollama=True):
        self.llm_responder = None  # 延遲初始化
        self.persona_loader = None  # 延遲初始化
        
    async def load_personality_profile(self, persona_id: str):
        # 在第一次使用時才初始化
        if self.persona_loader is None:
            self.persona_loader = PersonaLoader()
        # ...
```
這種延遲初始化模式與全域單例模式混用，增加了複雜度。

#### **影響：**
- **難以追蹤初始化順序：** 開發者不清楚哪些物件會在何時被創建
- **單元測試困難：** 無法輕易 mock 全域物件
- **隱藏的耦合：** 修改一個模組可能影響其他看似無關的模組
- **啟動失敗風險：** 如果某個全域物件初始化失敗，整個應用無法啟動

#### **建議改進方向：**
- 使用**依賴注入**（Dependency Injection）
- 使用 FastAPI 的 `Depends()` 機制
- 或者實作一個統一的 **ServiceManager** 類別

---

### ⚠️ 問題 3：職責不清與重複程式碼

#### **問題描述：**
多個模組的職責重疊，同樣的功能在不同地方重複實作。

#### **具體案例：**

##### 案例 1：對話管理重複
專案中有 **3 個** 對話管理器：

1. **PersonaDialogueManager**（persona_dialogue.py）
   - 管理雙人對話
   - 處理對話歷史
   - 整合 Unity 記憶

2. **GroupDialogueManager**（backend.py 中定義）
   - 管理群組對話
   - 處理對話歷史
   - **程式碼幾乎與 PersonaDialogueManager 重複**

3. **ChatWith**（chat_with_persona.py）
   - 也處理對話
   - 載入 RAG 資料庫
   - 檢索記憶

**問題：** 這三個類別都在做類似的事情（管理對話、載入記憶、生成回答），但彼此獨立實作，導致：
- 相同邏輯重複寫了三次
- 修改一個需要同步修改其他
- 不清楚該使用哪一個

##### 案例 2：代理人概念混亂
專案中有 **多個** Agent 概念：

1. **AgentStatus**（life_simulation_backend.py）
   - 用於生活模擬
   - 有 position, health, energy, happiness 等屬性

2. **Agent**（scenario_simulator.py）
   - 用於火災場景模擬
   - 有 location, panic_level, health, escaped 等屬性

3. **角色生成的 Persona**（humanoid_generator.py）
   - 儲存在 JSON 檔案中
   - 有基本資料、人格屬性、背景故事

**問題：**
- 這些 Agent 概念彼此獨立，沒有統一的數據模型
- `AgentStatus` 和 `Agent` 應該可以共用一個基礎類別，但沒有這樣設計
- 從 Persona 到 Agent 的轉換邏輯散落在各處

##### 案例 3：位置管理重複
位置資訊在多個地方被管理：

1. **SmartLocationManager**（location_function_tools.py）
   - 管理位置資訊和角色位置記憶
   - 有 `DEFAULT_LOCATIONS` 字典

2. **AgentStatus.current_location**（life_simulation_backend.py）
   - 儲存角色當前位置（字串）

3. **Agent.location**（scenario_simulator.py）
   - 火災場景中的位置（字串）

4. **LLMScheduler.location_types**（llm_scheduler.py）
   - 又定義了一套位置類型映射

**問題：**
- 位置資訊不統一，字串命名不一致
- 位置管理邏輯散落在多個模組
- `SmartLocationManager` 存在，但其他模組沒有使用它

##### 案例 4：LLM 呼叫封裝重複
幾乎所有需要使用 LLM 的類別都繼承自 `LLM_responder`：

```python
class StoryGenerator(LLM_responder): ...
class ToneGenerator(LLM_responder): ...
class Interviewer(LLM_responder): ...
```

**問題：**
- 繼承是為了重用方法，但這些類別本質上不是「IS-A」關係
- 應該使用**組合（Composition）**而非繼承
- 導致類別層次混亂

#### **影響：**
- **程式碼冗餘：** 同樣的邏輯寫了多次
- **維護成本高：** 修改一個功能需要在多處同步
- **容易出現 bug：** 不同實作的邏輯可能不一致
- **新人學習困難：** 不知道該使用哪個類別/函數

#### **建議改進方向：**
- **抽取共用基礎類別：** 為 Agent 建立統一的數據模型
- **統一對話管理：** 合併三個對話管理器，抽取共用邏輯
- **使用組合代替繼承：** LLM 呼叫應該作為依賴注入，而非繼承
- **位置資訊統一管理：** 所有模組都使用 `SmartLocationManager`

## 四、數據流向圖（文字版）

以下是專案中數據的流動路徑：

### 4.1 角色生成流程

```
【觸發】用戶請求 -> POST /api/humanoid/generate
          ↓
【Backend】backend.py 接收請求
          ↓
【生成器】character_generator.generate_persona()
          ↓
【步驟 1】BaseInfoGenerator.generate()
          → 生成基礎資料（姓名、年紀、性別、出生地）
          ↓
【步驟 2】AttributeInjector.inject()
          → 隨機選取人格特質、社交能力、能力屬性
          ↓
【步驟 3】StoryGenerator.generate()
          → 呼叫 LLM_responder.full_chat_gpt_4o()
          → OpenAI API 請求
          → 返回背景故事文字
          ↓
【步驟 4】ToneGenerator.generate()
          → 再次呼叫 LLM 分析語氣風格
          ↓
【步驟 5】SummarizedBehaviorGenerator.generate()
          → 總結行為模式
          ↓
【步驟 6】AIParameterAnalyzer.analyze()
          → 分析 AI 參數（語氣、情緒等）
          ↓
【儲存】寫入 JSON 檔案
          → humanoid/humanoid_database/{id}_{name}.json
          ↓
【返回】API 回應（包含完整角色資料）
```

**關鍵數據物件：**
- 輸入：無（系統自動生成）
- 中間數據：字典（dict）逐步累積資料
- 輸出：JSON 檔案 + HTTP 回應

---

### 4.2 對話生成流程（Unity 模式）

```
【觸發】Unity 客戶端 -> POST /persona-dialogue
          ↓
【Backend】backend.py 接收請求
          → 從請求中提取：
            - persona1_id, persona2_id
            - current_topic（對話主題）
            - unity_memory_context（Unity 記憶）
          ↓
【管理器】dialogue_manager = PersonaDialogueManager()
          ↓
【初始化】dialogue_manager.initialize()
          → 創建 ChatWith 實例
          → chatbot = ChatWith()
          → 等待 chatbot.wait_until_ready()
            ↓
            【載入】persona_loader_obj = PersonaLoader()
                    → 讀取 humanoid/humanoid_database/*.json
                    → 建立記憶體快取（personas 字典）
          ↓
【步驟 1】dialogue_manager.get_persona_context()
          → 為 persona1 獲取上下文
            ↓
            【RAG 檢索】
            interviewer_obj.load_rag_database(persona1_id)
              → 載入 FAISS 索引：interviewer/rag_database/{id}/index.faiss
              → 載入文檔：interviewer/rag_database/{id}/qa_pairs.json
            ↓
            interviewer_obj.retrieve_similar_docs(current_topic, index, docs)
              → 呼叫 LLM 生成 query embedding
              → FAISS 向量檢索（K=2）
              → 返回最相似的 2 個文檔
            ↓
            【記憶整合】
            - 如果有 unity_memory_context，優先使用
            - 加入對話歷史（最近 5 輪）
            - 返回：(conversation_context, retrieved_docs)
          ↓
【步驟 2】dialogue_manager.generate_persona_response()
          → 為 persona1 生成回應
            ↓
            【建立 Prompt】
            interviewer_obj.build_simulation_prompt(
              persona_data,
              retrieved_docs,
              current_topic
            )
              → 使用 prompt_loader 載入系統提示詞
              → 組合：系統提示 + 記憶上下文 + 用戶問題
            ↓
            【LLM 請求】
            interviewer_obj.simulate_persona_answer(prompt)
              → 呼叫 LLM_responder.full_chat_gpt_4o()
              → OpenAI API 請求
              → 返回角色回應文字
          ↓
【步驟 3】重複為 persona2 執行步驟 1-2
          ↓
【儲存】如果需要，儲存對話歷史
          → dialogue_manager.save_dialogue_history(session_id, history)
          → 寫入 conversation_history/dialogue_{session_id}.json
          ↓
【返回】API 回應
          → persona1_response, persona2_response
```

**關鍵數據流：**
1. **Persona 資料：** JSON 檔案 → PersonaLoader → 記憶體字典

3. **Unity 記憶：** Unity 發送 → 整合到上下文 → LLM prompt
4. **對話歷史：** 本地 JSON 檔案 → 記憶體 → 上下文
5. **LLM 呼叫：** Prompt → OpenAI API → 回應文字

### 4.3 生活模擬流程

```
【觸發】GET /api/life-simulation/start

          ↓
【管理器】life_simulation_manager.start_simulation(request)
          ↓
【步驟 1】創建代理人
          → create_default_agents(count=3)
            ↓
            【預設 Persona ID】
            default_personas = ["687a1b2d5b", "867b21d0fe", "eef4720230"]
            ↓
            【載入名稱】
            name = await get_persona_name(persona_id)

            ↓
            【創建狀態】
            agent = AgentStatus(
              agent_id = f"agent_{i+1}",
              persona_id = persona_id,

              current_location = "home",
              health = random(80, 100),

              ...
            )
            ↓
            【儲存】

          ↓
【步驟 2】啟動模擬循環

            【無限循環】while simulation_active:
              ↓
              【計算時間】
              delta = (now - last_tick) * time_speed
              current_time += delta
              ↓
              【更新代理人】
              for agent in agents.values():
                update_agent_status(agent)
                  → 根據活動類型更新屬性
                  → 如：sleep -> energy += gain

【返回】API 回應（agents 列表）
```

### 4.5 火災場景模擬流程

```
【觸發】POST /api/simulation/start
          ↓
【Backend】backend.py 接收請求
          ↓
【創建模擬】
          simulator = FireScenarioSimulator()
          await simulator.initialize()
            ↓
            【載入 Persona】
            persona_loader = PersonaLoader()
            await persona_loader.wait_until_ready()
            ↓
            【初始化對話】
            chatbot = ChatWith()
            await chatbot.wait_until_ready()
            ↓
            【建立環境】
            _create_environment()
              → 建立房間圖（rooms 字典）
              → 建立連接圖（connections 字典）
          ↓
【步驟 1】創建代理人
          → create_agents_from_database(num_agents=5)
            ↓
            【隨機選取 Persona】
            all_personas = persona_loader.get_all_personas()
            selected_personas = random.sample(all_personas, 5)
            ↓
            【建立 Agent】
            for persona in selected_personas:
              initial_location = random.choice(possible_locations)
              agent = Agent(persona_id, persona, initial_location)
              agents.append(agent)
              rooms[initial_location].agents.append(agent.id)
          ↓
【步驟 2】設定火災
          → set_fire(room_name)
            → rooms[room_name].on_fire = True
            → rooms[room_name].temperature += 100
          ↓
【步驟 3】執行模擬循環
          → async for tick in range(max_ticks):
              ↓
              【環境更新】
              for room in rooms.values():
                if room.on_fire:
                  room.temperature += random(10, 20)
                  room.visibility -= random(10, 30)
                if room.smoke:
                  room.visibility -= random(5, 15)
              ↓
              【代理人決策】
              for agent in agents:
                if agent.escaped or agent.injured:
                  continue
                ↓
                【更新狀態】
                agent.update_status(current_room)
                  → 根據環境影響 health, panic_level
                ↓
                【LLM 決策】
                action = await decide_action_llm(agent, environment_info)
                  ↓
                  【建立 Prompt】
                  prompt = f"""
                  你是 {agent.name}...
                  當前狀態：位置={agent.location}, 恐慌={agent.panic_level}
                  環境：{room.temperature}度, 能見度={room.visibility}
                  可見房間：{visible_rooms}
                  請決定行動：移動到哪裡？
                  """
                  ↓
                  【LLM 請求】
                  llm_responder.full_chat_gpt_4o(prompt)
                    → OpenAI API
                    → 返回決策文字
                  ↓
                  【解析決策】
                  parse_action(response_text)
                    → 提取目標房間
                ↓
                【執行行動】
                if action == "move_to":
                  agent.location = target_room
                  agent.add_log(tick, "移動", f"到 {target_room}")
              ↓
              【事件通知】
              if use_sse:
                yield SSE event（即時推送給前端）
          ↓
【儲存結果】
          → save_simulation_results()
            → simulation_results/{simulation_id}.json
          ↓
【返回】模擬結果摘要
```

**關鍵數據流：**
1. **Persona 資料** → Agent 初始化 → **場景代理人**
2. **環境狀態**（rooms）→ 持續更新 → **影響代理人**
3. **代理人狀態 + 環境** → Prompt → **LLM 決策**
4. **LLM 決策** → 解析 → **行動執行**
5. **模擬事件** → SSE → **即時推送前端**
6. **完整記錄** → JSON 檔案 → **存檔**
